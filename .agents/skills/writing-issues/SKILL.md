# Writing Issues

This skill captures the house style for GitHub issue titles and bodies in the UAMS-Web
repositories. An issue is a brief for whoever picks it up: often an autonomous agent. Write it
so the work is unambiguous before anyone touches code: state the *why*, pin down the *current*
behavior, describe the *desired* outcome, and bound the scope explicitly. The defining feature
of a good issue here is a crisp, testable **Acceptance criteria** checklist.

This is the sibling of [`writing-pull-requests`](../writing-pull-requests/SKILL.md) and
[`writing-commits`](../writing-commits/SKILL.md); the inline-code, file-link, bullet, and
punctuation conventions are shared with those skills; for em dashes see
[`no-em-dashes`](../rule-no-em-dashes/SKILL.md). When in doubt, match those skills.

## Start from the archetype template

Where the repository carries `.github/ISSUE_TEMPLATE/` skeletons: one Markdown file per
archetype: `1-bug.md`, `2-feature.md`, `3-research-spike.md`, `4-follow-up-cleanup.md`: a
human filing through the web UI gets one pre-filled, and **you should start from the matching
file too**, so both paths produce the same shape. Copy it, fill it in, strip the `<!-- … -->`
guidance, and pass the result to `--body-file`. Where an issue doesn't fit an archetype (a
content or data task, a blueprint normalization, an endpoint ticket, a toolchain task), or the
repository has no templates, build the body from the section inventory below.

**This skill is the source of truth; the templates carry only the skeleton and a pointer back
here.** When the house style changes, change it here first and reconcile the template, never
the reverse, or the two silently diverge.

## Output format

When proposing an issue, give the **title** on its own line and present the **body as a single
fenced Markdown code block** so it can be pasted into `gh issue create` (or the web UI). The
body is GitHub-Flavored Markdown, never include an `H1` (`#`) heading; GitHub renders the title
separately. Top-level sections are `##`, sub-sections `###`.

When you create the issue yourself with `gh`, **write the body to a file and pass `--body-file`
from the start** (as the recipe below does): never inline the Markdown via `--body`. Issue
bodies are dense with backticks, `$`, `!`, backslashes, and fenced code blocks, every one of
which the shell mangles or errors on as an inline argument (the failure is intermittent, so
inline `--body` looks fine until a body finally trips it). `--body-file` sidesteps it entirely,
and the same holds for `gh issue edit <n> --body-file`.

Creating the issue is half of filing. *Filing into the project board* below is the other half,
done in the same pass, not a follow-on step.

## The disclaimer rule (non-negotiable)

**Never** add a `> *This was generated by AI during triage.*` blockquote (or any equivalent
"written/generated by AI" line) to an issue body. Some existing issues still carry it from an
earlier triage flow: do not replicate it, and strip it when rewriting an issue.

## Titles

The title is an imperative, verb-first phrase naming the deliverable or the outcome: what the
issue *accomplishes*, not a topic label. No trailing period. Keep it specific and scannable.

- **Default form: imperative outcome:** `Harden `assets:sync-from-yaml` against stale-cache id collisions`,
  `Render quiz fieldtype on public forms`, `Convert legacy Bard `video` set blocks to `youtube`/`vimeo`/`box` sets`,
  `Format footer phone number for display (E.164 → national)`, `Stop writing orphaned alt/caption/exempt meta for logo uploads`,
  `Deduplicate news.uams.edu posts`, ``Page attachments by `ID` ascending so a live edit cannot skip one``,
  ``Stop dropping underscore-prefixed postmeta from the posts payload``.
- **Bugs may lead with the symptom** instead of an imperative, naming the faulty component and
  the user-visible consequence: `GlobalOrigin tag returns null (not '') in non-recursive mode, crashing email render`,
  `Fix replicator search transformers reading the wrong row handle`.
- **Disambiguating parenthetical**: append the mechanism in parens when it sharpens the title:
  `(E.164 → national)`, `(string "1" vs boolean)`, `(not '')`.
- **Inline code in titles**: backtick anything a developer would type or grep: commands
  (`assets:sync-from-yaml`), collection/field handles (`people`, `digital_source_type`,
  `hide_from_menu`), meta keys (`options_*`), set names (`youtube`/`vimeo`/`box`).
- **No Conventional-Commit prefixes.** Never prefix an issue title with `feat:` / `fix:` /
  `chore:` etc. those belong on commits, not issues. A handful of older titles carry them
  (e.g. `fix: primary nav ignores hide_from_menu …`); strip the prefix when rewriting and
  fold the verb into the imperative phrase (`Fix primary nav ignoring …` or
  `Stop primary nav ignoring …`).

Recurring title families with fixed shapes:

- **Research spike:** prefix with `Research:`: `Research: decide Elavon integration + PCI approach for Statamic form payments`,
  `Research: how much of ACF PRO's REST layer should the migration API reuse?`.

## Body: the standard skeleton

Most issues follow this spine. Drop the sections that don't apply; never drop **Acceptance
criteria**.

1. **Lede**: 1–3 sentences. Frame the problem and the desired outcome. Lead with the
   user-visible effect or root cause, not the implementation. The lede frequently opens with a
   **provenance line**: `Follow-up to #589.`, `Spun off from #489.`, `Part of #358.`,
   `Discovered while validating … for #706.` A provenance line says where the issue *came
   from*; it never states a dependency: see *Dependencies belong in the edges*.
2. **Context**: `## Why` (motivation, often the strongest section on a feature) and/or the
   current-state sections below.
3. **Desired outcome / plan**: `## What we're building`, `## Scope`, `## Approach`,
   `## Proposed fix`.
4. **`## Acceptance criteria`**: mandatory. A GitHub task-list of observable outcomes.
5. **`## Out of scope`**: explicit non-goals, each pointing at its tracking issue.
6. **`## References`**: links, file paths, sibling/companion tickets.
7. **No relationship line.** Dependencies live in GitHub's native dependency edges
   (`blocked_by` / `blocking`) and are **never** restated in the body: see
   *Dependencies belong in the edges* below.

## Section inventory

Use the section that fits; these are the established names (don't invent synonyms casually):

- **`## Why`**: why this matters now. On features this carries the weight: explain the forces
  that make the work necessary (e.g. "two upstream sources guarantee duplicate `people`
  clusters").
- **`## Background`**: domain context for content/data tasks.
- **`## Current state`** / **`## Current behavior`**: what exists today, with file/handle
  references. The factual baseline the work changes.
- **`## The bug`** / **`## Root cause`** / **`## Reproduction`**: bug issues only. `## The
  bug` / `## Root cause` walk the mechanism (quote the offending code in a fenced block);
  `## Reproduction` gives the concrete trigger and the observed error.
- **`## Desired behavior`**: the target contract, stated as behavior not implementation.
- **`## What we're building`** / **`## What to upload`** / **`## Target behavior`**: the
  deliverable for features/content tasks (tables are welcome for concrete URL/field mappings).
- **`## Scope`**: a bounded list of the changes the issue covers (common on follow-up
  cleanups).
- **`## Approach`** / **`## Proposed approach`** / **`## Chosen approach`** / **`## Proposed
  fix`** / **`## Fix`**: the recommended path. Name the design decision and why; include
  before/after code where it removes ambiguity. For a fix already made, `## Fix` describes what
  was done.
- **`## Questions to resolve`**: research spikes: the numbered open questions the spike must
  answer.
- **`## Methodology`** / **`## Definitions`**: content tasks: the step-by-step procedure and
  the terms it relies on.
- **`## Acceptance criteria`**: see below. Always present.
- **`## Out of scope`**: first-class. Each deferred item links the issue that owns it (or says
  "file a follow-up").
- **`## References`**: bullet list: source files (linked), the companion tickets in sibling
  repositories this work serves, sibling tickets, external docs/URLs.
- **`## Notes`**: caveats, edge cases, "worth a follow-up" asides.
- **`## Test plan`** / **`## Files`**: optional, used when the issue doubles as the working
  record of an in-flight change (mirrors the PR conventions; `[x]` for already-done).

## Acceptance criteria: the core of every issue

This is the section that makes an issue actionable. Conventions:

- A GitHub **task list** (`- [ ]`), one box per independently verifiable outcome. Use `- [x]`
  only when the issue records work already completed.
- Each item is an **observable outcome**, not an implementation step. "Running the command
  against a cache with stale rows leaves exactly one row per YAML file afterward", not "add a
  truncate call".
- Be concrete: name the command, the URL, the field, the file, the rendered result, the error
  that must no longer throw.
- **Bound the behavior on both sides**: assert the new behavior *and* assert the unaffected
  cases still hold ("logo uploads write none of the three keys; content-image uploads still
  do").
- **End with a test/coverage item.** Nearly every issue closes its AC list with a regression or
  feature-test requirement ("A test covers the id-reassignment case and the orphan-pruning
  case").
- For research spikes, the AC are **decisions documented**, not code ("a PCI-compliant
  integration pattern is chosen and documented", "a clear go / no-go recommendation is
  recorded").
- **On a `decision-fork` ticket the criteria describe a decision being recorded and its
  follow-ups existing, never a build being done.** "The chosen approach is recorded here and
  in the decision log with the rejected alternatives" and "a follow-up exists for each piece of
  work the decision unblocks" are the shape. A criterion that can only be ticked by writing
  code is the signal that the ticket is carrying work belonging in one of those follow-ups
  (see [`design-decision-forks`](../rule-design-decision-forks/SKILL.md)).

## Keep the body current: comments are for deliverables, not for findings

**The body is the ticket.** When work produces a finding, a correction, or a change to the
acceptance criteria, **rewrite the body**. A comment is the wrong home for it.

**Why this is non-negotiable rather than tidiness.** Whoever picks the ticket up later reads the
body: often an autonomous agent working from it as a brief. Anything parked in the comment
thread may simply not be seen, so a body still arguing from a superseded premise is what
actually gets acted on. The failure is silent and it compounds: each correction posted as a
comment makes the body *more* wrong while the thread makes it *look* thoroughly investigated.

Observed on `wordpress-importer#668`, where the premise moved four times across four comments: 
including a fourth option investigated and rejected: while the body still presented the
original three-option comparison built on two facts that no longer held. A reader following the
standing instruction to work the body would have re-proposed the rejected option.

### What goes where

| | Home |
| --- | --- |
| A finding, measurement, or verification result | **The body**: as a `## Findings` section or folded into the section it corrects |
| A correction to a premise the ticket rests on | **The body**: restate the premise; don't append a contradiction below it |
| A decision, its reasoning, and the rejected alternatives | **The body**: plus the repository's decision log |
| A change to what "done" means | **The body**: amend the acceptance criteria in place |
| A rejected option, and why | **The body**: otherwise it gets re-proposed |
| The deliverable itself: a run was made, a PR opened, a handover from another repo's session | **A comment** |

### How to apply

- **Restate, don't append.** Replacing "no export exists for this site" beats leaving it and
  adding "actually, 28 section exports exist" below: the second form leaves both readings on
  the page and makes the reader adjudicate.
- **Amend the acceptance criteria in the same change.** Ticking a box in a comment does not tick
  it; the checklist a reader sees is the one in the body.
- **Record rejected options with the reason**, not just the verdict: an option rejected for a
  reason nobody can see is an option someone re-proposes.
- **Keep a correction history when the premise moved more than once.** *How* a ticket's
  understanding changed is often its most reusable content, and it is exactly what a comment
  thread buries.
- **Edit with `--body-file` / `-F body=@file.md`**, never inline: same reason as filing (see
  *Output format*).
- **A comment that is still worth posting must leave the body standing on its own.** The test:
  if every comment were deleted, would the ticket still be correct and complete? If not, the
  body is not finished.

## Relationships and cross-references

### Dependencies belong in the edges, never in the body

**Never write `Blocked by #N.` or `Blocks #N` into an issue body.** Express a dependency
*only* as a native GitHub dependency edge (`dependencies/blocked_by`, `dependencies/blocking`).

**Why.** Prose and edges drift apart, and the prose is the half that fails silently: the edge
is machine-maintained, the sentence is not. Found across one review pass in
`wordpress-importer`: `#589` named a **closed** decision ticket as its gate while its real edge
pointed elsewhere; `#601` listed four blockers of which two had closed; `#695` warned that its
blocker "lives in another repository, so there is no `blocked_by` edge to hang it on", which is
not true, edges are cross-repo, and that blocker had already shipped; six post-type issues each
carried a *cleared* gate as an unchecked acceptance criterion. In every case the edge was right
and the sentence was wrong.

There is a second, sharper failure the prose form invites: **a bare `#N` resolves against the
current repository.** `wordpress-importer#432` cited `#215`/`#216` for an "empty-entry
redirect"; in that repo those are unrelated migrate-content issues, and the real referents were
`uams-statamic#215`/`#216`. An edge stores a repository-qualified object id and cannot make that
mistake.

**The carve-out: context cross-references stay.** What is banned is the *dependency claim*,
not the reference. These remain welcome, because the graph does not track them and they cannot
fall out of sync with it:

- **Provenance**: `Follow-up to #589.`, `Spun off from #489.`, `Part of #358.`
- **Inline cross-refs**: `tracked in #N`, `tracked separately in #N`, `see #802 / #803`.
- **Naming what something is**: "the contract this codes against is `#589`", "`uams-statamic#295`
  decides what these fields map to".

Where a body needs to explain *why* something waits, describe the **condition**: what has to be
true, what artifact must exist: rather than naming a ticket as the gate.

**If the prose is right and the graph is not, add the missing edge.** Do not keep the sentence
as a substitute for the edge it is describing.

### Reference forms

- **Cross-repo refs**: the sibling-repo form is `Org/Repo#N`, either bare
  (`UAMS-Web/wordpress-importer#19`) or as a backticked link where it reads better
  (`` [`wordpress-importer#10`](https://github.com/UAMS-Web/wordpress-importer/issues/10) ``).
  Qualify **every** cross-repo reference: a bare `#N` silently resolves against the repository
  the body lives in.
- **In `## Out of scope` / `## References` bullets**: end the bullet with `, tracked in #N.`
  so the residual work visibly has a home.

## Inline code, links, bullets

Shared with `writing-pull-requests`: the short version:

- **Backtick aggressively**: file paths, class/method names, collection and field handles, post
  types and taxonomies, meta keys (`_thumbnail_id`), hook names (`rest_pre_dispatch`),
  fieldtypes, template tags (`{{ global_origin }}`), config keys (`embed_mode: full`,
  `per_page_max`), commands (`php artisan test`, `composer test`), env vars, constants,
  version arrows (`` `6.18.1` → `6.19.0` ``).
- **File paths are linked.** Prefer the **absolute branch URL** target
  (`` [`path/to/file.php`](https://github.com/UAMS-Web/<repo>/blob/main/path/to/file.php) ``,
  `/tree/` for directories), exactly as the PR skill specifies; vendor refs may include line
  anchors (`…/GlobalOrigin.php#L205-L217`). Relative-path links appear in some issues but the
  absolute-branch form is the target to standardize on.
- **Fenced code blocks** (`php`, `antlers`, `yaml`, `html`, `json`, `neon`, `bash`) quote the
  offending or proposed code in bug issues, and config/template/payload excerpts elsewhere.
  Show before/after as two labeled blocks or inline-commented code, not a `diff` block.
- **Bullets are `-` only**, nested with a 2-space indent. **Bold-tag lead-ins**
  (`- **Per-field source of truth:** …`) categorize list items. **No em dashes** in body prose;
  use a colon after the bold tag (see [`no-em-dashes`](../rule-no-em-dashes/SKILL.md)). **Don't force-wrap** prose.
- **Tables** for naturally tabular data: entry→URL maps, field inventories, variant matrices.

## Labels

Apply the repository's own labels that match the issue's nature (multiple are normal).
`gh label list -R UAMS-Web/<repo>` shows the set. **Don't invent labels the repository doesn't
have**: where none fits, file the issue with no label rather than create one. A bug is told apart
by the GitHub **issue type** `Bug`, not by a label (see *Filing into the project board*).

### Execution mode: `afk` / `hitl`

This repository does not carry the `afk` / `hitl` labels, so file without them and do not create
them. Classify the issue all the same: the classification below decides whether an agent may
build it. Where the text below applies or flips a label, record the classification in the body
instead: a `hitl` issue says what a human must decide or do, in its `## Decisions to resolve`
section or its opening paragraph.

**The exception is `epic`.** An issue labeled `epic` is exempt from the requirement: it is a
container whose slices each carry their own execution mode, not a unit of work anyone picks up
and builds. An epic with neither label is **correctly labeled**: don't "fix" it. Apply `hitl` to
an epic only where the container *itself* waits on a human (`uams-statamic#1777` and
`uams-statamic#1045` both wait on a real-world action).

- **`afk`** (away-from-keyboard): buildable autonomously: the design is **pinned or already
  decided**, or the fix is **fully specified**, so there is **no genuine design fork to resolve
  in the issue's own scope** ("follow the established spec / the pinned standard"). Most build
  slices, dependency bumps, refactors, and already-specified bug fixes are `afk`. The test:
  *could a competent agent finish this alone, without a human deciding anything or doing
  anything outside the repo?* If yes → `afk`. **Posting to a third-party tracker does not, on
  its own, make an issue `hitl`**: an upstream issue, a pull request, a comment, an upvote or a
  feature request is `afk`: the agent researches, drafts and prepares it, and a human approves
  the post before it goes out (`uams-statamic#2772`).
- **`hitl`** (human-in-the-loop): completing it **requires a human in the loop**, for either
  reason: a human **decision**: an unresolved design fork (the issue carries a `## Questions to
  resolve` / `## Decisions to resolve` section), a policy / cost / go-no-go call, or a settled
  decision being re-opened; or a real-world **action**: a step outside the repo a coding agent
  can't perform (a deploy, provisioning / credentialing, standing up a service, creating an
  external account, recruiting a person, installing an app, producing a content export, running
  or verifying a live test-import). If a human must **decide or act** before the issue can close
  → `hitl`. The one carve-out: posting something an agent has prepared to a third-party tracker
  is not a real-world action in this sense, because the human's part is approving the post, not
  doing the work, so such an issue is `afk` (see above). There is no separate `operational`
  label; a real-world action is `hitl`.

For the **decision** flavor, the issue carries `decision-fork` alongside `hitl`. Surface the fork
the right way: lead with a compare/contrast packet, *then* the interactive prompt : following
the [`design-decision-forks`](../rule-design-decision-forks/SKILL.md) rule, which defines that
process and the label's lifecycle (don't restate either here).

**A `decision-fork` ticket delivers two things and nothing else: the decision, recorded: what
was decided, why, and the rejected alternatives, and the follow-up tickets it produces.** Build
work the decision unblocks goes into those follow-ups, blocked by the fork through native
dependency edges. Its acceptance criteria therefore describe *a decision being recorded and its
follow-ups existing*, never a build being done: a criterion naming a file to change belongs on
a follow-up. Fused, the build half inherits the decision half's latency and nothing on the board
signals that it has. The [`design-decision-forks`](../rule-design-decision-forks/SKILL.md) rule
carries the reasoning and the worked instance; the point here is what the ticket may contain.

**How to classify**: a **leaf** issue takes the mode of what *its own* completion needs; don't
inherit a blocker's mode (blockers carry their own labels). An **`epic`-labeled container** is
exempt (see above): classify its slices, not the container. When genuinely on the fence, prefer
`hitl`: it's safer to route an ambiguous issue to a human than to let an agent build past an
unmade decision.

**Keep the label current: flip it when the classification changes (standing rule).** Flip
`hitl` → `afk` once the fork is **decided and recorded** on the issue: relabel and reconcile the
body in the *same change* (retire the `## Questions to resolve` / `## Decisions to resolve`
section, tick the decision-recorded acceptance-criteria item). What remains on a fork ticket
after the flip is filing its follow-ups, not building them; the build moves into follow-up
tickets this ticket files, blocked by it through native dependency edges, and the ticket closes
once the decision is recorded and those follow-ups exist. The `decision-fork` label stays on
through the flip; its lifecycle, and why, is in the
[`design-decision-forks`](../rule-design-decision-forks/SKILL.md) rule. Flip `afk` → `hitl` the
moment work **surfaces a genuine design fork** an agent shouldn't decide alone: relabel (adding
`decision-fork`), add a `## Decisions to resolve` section, and settle it with the user (per
[`design-decision-forks`](../rule-design-decision-forks/SKILL.md)) before building.

## Epics and sub-issues

An **`epic`** is a container. It holds the shared context a body of work rests on and **carries
no deliverables of its own**: no acceptance criteria, no "decisions taken here", nothing anyone
could pick up and build. Every deliverable is a sub-issue. If a reader cannot tell what to *do*
from a slice alone, the slice is under-written, not the epic.

That constraint is what makes an epic useful. A container with its own checklist competes with
its slices, and the work ends up recorded in two places that drift.

**When a ticket becomes an epic.** Convert one when it has accumulated several independently
shippable deliverables: usually visible as an acceptance-criteria list whose items would each
make a reasonable ticket. Two shapes recur:

- A **decision plus its build.** Spin the decision into its own gating slice rather than leaving
  it at the head of the container, so the fork is something a human can be handed and the epic
  is not itself `hitl`.
- **Measurement, decision, then build.** File the measuring slices even when they are already
  done: see below.

**File retroactive sub-issues for work already finished.** When converting a ticket that has
already produced results, give each completed piece its own sub-issue, record what it found in
the body, and close it as `completed`. It costs a minute and it gives the finding a home: an
epic body is a poor place for a measurement, because the next edit overwrites it.

**Labels on a container.** An `epic` takes the topic labels that describe its subject and
**not** `afk` / `hitl` (see the execution-mode exception above), nor labels that describe how
its slices will be worked: `research`, `decision-fork` and similar belong on the slices that
earn them.

**Wiring, and it is not the same thing as a dependency.** A sub-issue says *this is part of
that*; a `blocked_by` edge says *this cannot start until that finishes*. Most epics need both,
and they are set independently: a `blocked_by` edge does not imply membership or vice versa:

```bash
id=$(gh api repos/{o}/{r}/issues/<child> --jq '.id')     # numeric .id, NOT the issue number
gh api -X POST repos/{o}/{r}/issues/<parent>/sub_issues -F sub_issue_id=$id
```

**Sub-issues work across repositories.** The endpoint keys on the global database id, so a slice
living in a sibling repo attaches to an epic here exactly like a local one, and a deliverable
here attaches to an epic that lives elsewhere. Use it: a deliverable that belongs to an epic but
ships from a sibling repository is still that epic's slice, and a relationship stated only in a
body is one nothing can query, lost the next time either body is rewritten.

Read the set back with `GET …/sub_issues`, and see
[`github-api-budget`](../rule-github-api-budget/SKILL.md) for why these are REST calls.

## Board `Status`: the transition table

`Status` moves in lockstep with the branch, on any ticket. Flip it as the work moves, not in a
sweep afterwards; [`closing-a-ticket`](../rule-closing-a-ticket/SKILL.md) owns why that matters.

| When | Status | Also |
| --- | --- | --- |
| Filed, not yet started | `Todo` | add the issue to the project (see below) |
| Starting work | `In Progress` | add to the project if absent |
| Merged into an integration branch, awaiting the gate | `CI` |: |
| Merged to `main` | `Done` | GitHub auto-closes the issue from `Closes #N` |
| A blocker surfaces mid-flight | `Blocked` |: |

## Check for an existing issue first

Before creating any issue, search the tracker for one that already covers the same **concept**: 
match on the idea, not just the title, since an existing issue may be worded completely
differently. Run a few searches with varied terms, and **include closed issues and pull
requests** (a fixed or won't-fix issue still means *don't* refile, and an open PR means the work
is already done):

```bash
q() { gh api "search/issues?q=repo:UAMS-Web/<repo>+$1&per_page=100" \
        --jq '(.items[] | "\(.number) \(if .pull_request then "PR   " else "issue" end) \(.title)"),
              "-- shown \(.items|length) of \(.total_count) --"'; }

q '<symptom or feature>'
q '<affected file / handle / symbol>'
q '<class or label, e.g. SSRF, form-emails>'
```

**`per_page` and the trailing count are both load-bearing; without them this check silently
answers a smaller question than it was asked.** `search/issues` returns one page, not a result
set, and reports the true figure in `total_count`; a `--jq` filter that selects only `.items[]`
discards the one field that would have said so, and the truncated output is byte-identical in
shape to a query that genuinely found everything. Measured in `wordpress-importer` on macOS
(Darwin 25.6.0), 2026-09-06, running the earlier count-less form verbatim: `q 'importer'`
printed **30** rows for a query matching **658**, while a control on a small query: `q 'XXE'`,
3 matches: printed all 3, which is why this survived: the recipe is correct whenever a search
happens to return fewer than 30, and that is most searches. Measured in `uams-statamic` the same
day: `importer` reports **541 matches and prints 30**, while `schema jsonld` reports **8 and
prints 8**. Nothing but the total distinguishes them, and the totals move (those two figures
were 524 and 7 when first measured), which is why the denominator is printed rather than
remembered.

**A total greater than the rows shown means the check has not answered the question.** Either
paginate (`&page=2`, until a short page) or narrow the query until the total fits: "nothing
matches" is not a conclusion you can draw from a truncated page. A duplicate check that fails
toward *nothing matches* fails in the one direction that causes a duplicate filing.

The parentheses around the item stream are not cosmetic: without them `.items[]` becomes the
scope for what follows, so `.items` and `.total_count` resolve to `null` and the trailer prints
once per hit reading `shown 0 of null`. Verified by running both forms.

The count goes **after** the hits rather than before them. A header is easier to read and is the
first thing lost when the output is piped; a trailer is the first thing lost too, but its
absence is then conspicuous against a list that has obviously been cut. Neither placement
survives a `head`, which is the second-order truncation `wordpress-importer#965` documents: the
caller's own pipeline cuts what the endpoint did not. When you don't have the count line: 
reading a transcript after the fact, say: the tell is a page of results that is *exactly*
`per_page` long.

**`incomplete_results` is not that signal and must not be used as one.** It reports a
server-side timeout, not pagination, and it is `false` on exactly the truncated responses
described above.

Output labels each hit, so a pull request is visible as one rather than silently absent:

```
891 PR    Record the concurrent-write hazard on shared mutable state
881 issue Document the concurrent-write hazard on shared mutable state in `.claude/rules/`
```

**Do not use `gh issue list --search` or `gh search issues` for this.** Both filter pull requests
out, so a session following them is told nothing exists while an open PR is already fixing the
thing: measured in `wordpress-importer`, the same query returned 8 hits through `gh issue list`
and 16 through the form above, 7 of them pull requests. The hole is in those CLI wrappers rather
than in the endpoint: `gh api search/issues` and `gh api repos/{o}/{r}/issues` both return the
two kinds, and the `.pull_request` key is what distinguishes them. `gh issue list --search` is
also GraphQL-backed, so it fails outright when the quota is gone while the REST form keeps
answering. The REST endpoint has its own limits, recorded in
[`github-api-budget`](../rule-github-api-budget/SKILL.md): it is an unordered AND over tokens and
cannot phrase-match (a quoted pair counts something wider than it appears to), and it indexes
comments, so a count taken from it is self-incrementing.

**Join a multi-word term with `+`, not a space.** The term sits inside a URL, so
`duplicate+check` searches for both words while `duplicate check` leaves a raw space in the
query string: measured in `uamswp-migration-api`, that does not error, it **hangs** with no
output until the command is killed.

**An empty result is only worth something if the query was shown to match.** Before accepting
one, run the same form against a term you know is present and confirm it returns the known item
: per `uamswp-migration-api#98`, an empty result from a query that cannot match is identical to
an empty result from an empty tracker.

Vary the terms across the symptom, the affected file/handle/symbol, and the class/label: one
query rarely surfaces a differently-worded dup. For work that spans repos, search the sibling
repo too (swap the `repo:` qualifier, e.g. `repo:UAMS-Web/wordpress-importer`). If anything
plausibly covers the concept: **link it and skip**, or add a comment / sharpen the existing
issue: don't open a duplicate. Only file once you've confirmed nothing matches.

## Filing into the project board

**A ticket is not filed until it is on the board with its `Status` set.** `gh issue create`
returns a URL and a number, and a number is not a filed ticket: an issue that exists on no board
is invisible in every view anyone plans from, and nothing downstream will ever say so. Creating
the issue is half of it; adding it to the project and setting `Status` is the other half, done in
the same breath as the labels and the issue type, not as a follow-up step. That is stated before
the mechanics because the mechanics are what get read, and a recipe answers *how* without ever
answering *whether*.

**Why this is stated and not left to the recipe below.**
[`closing-a-ticket`](../rule-closing-a-ticket/SKILL.md) requires the card to *move in step with the
branch*. That instruction presupposes a card, so a ticket filed without one satisfies it
**vacuously, and forever**: "move the card" cannot fail for a ticket that has no card, so the
omission cannot be detected from that rule's side. The two documents cross-refer and are
mutually consistent, and *creating* a card falls outside both, which is exactly what makes the
gap invisible from either end: a reader arriving at either one finds a pointer and concludes the
subject is covered.

**The omission is silent by construction.** A ticket with no card behaves normally in every other
respect: it can be filed, labeled, assigned, built, reviewed, merged and closed with nothing
ever surfacing the omission, and it passes every status-based check, having no status to be
wrong. So it is found only when somebody goes looking for something else. On 2026-09-05 at least
six `uams-statamic` tickets across three concurrent sessions were filed or delivered with no card
and found by hand within twenty minutes, only because an unrelated observation sent people
checking; the same day, five open `uamswp-migration-api` issues were on no project when swept,
and one had been reported as boarded by the session that filed it.

New issues are tracked on the **Statamic Migration MVP Development** project: 
`UAMS-Web/projects/1` (project node id `PVT_kwDOAUGyns4A1pdL`). After `gh issue create`, add the
issue to the board and set its `Status`. That is the only field to set: the board's other fields
are neither set nor read. The board is org-level and shared by every repository on it, so use
`--owner UAMS-Web` (not a repo) and the GraphQL API for reads.

**Everything in this section is GraphQL-only: Projects V2 has no REST surface.** That makes the
board the one thing a spent GraphQL quota genuinely blocks, so keep the budget for it: per the
[`github-api-budget`](../rule-github-api-budget/SKILL.md) rule, prefer REST for the issue calls that
have an equivalent (`gh issue create` / `edit` / `close` are all GraphQL-backed, and fail together
while REST is untouched), and check the budget the way that rule prescribes before a batch. The
quota is metered per user across the whole organization, not per repository, and the board is
shared: treat it as a resource you can exhaust for someone else, not just for yourself.

**Set the issue type too.** Separate from labels and from the board, GitHub carries an
org-level **issue type**: `Bug`, `Feature`, or `Task`, and it is *single-select*, so unlike
labels it cannot contradict itself. It matters more than the label vocabulary does for bugs,
since bugs are not filed under a label. Align it with the archetype you
filed: `Bug` → the bug template, `Feature` → the feature template, `Task` → a research spike or
a follow-up cleanup. The web-UI templates set it via their `type:` front matter; `gh issue
create` has no `--type` flag, so on the agent path set it with the API (step 1b in the recipe).

Issue types are **organization-wide**: the same three defaults apply in every UAMS-Web
repository, so adding a custom type is not a per-repository decision. The three defaults are
what we use.

**`Status`** (single-select): `Todo` · `Blocked` · `In Progress` · `CI` · `Done`. A
freshly-filed issue that isn't being worked yet is `Todo` (even if you've diagnosed it: 
diagnosis lives in the body, not the board). The transitions after that are the table above.

**Recipe:**

```bash
# 1. create + assign + label (pass a --label only for a label `gh label list` shows)
gh issue create --repo UAMS-Web/<repo> --title '…' --body-file body.md \
  --label <label> --assignee @me

# 1b. set the issue type (no `gh issue create --type` flag exists; Bug | Feature | Task)
gh api -X PATCH repos/UAMS-Web/<repo>/issues/<n> -f type=Task

# 2. add to the board → prints the item id (PVTI_…)
gh project item-add 1 --owner UAMS-Web --url <issue-url> --format json

# 3. set Status (Todo here; the ids are in the table below)
gh project item-edit --project-id PVT_kwDOAUGyns4A1pdL --id <item-id> \
  --field-id PVTSSF_lADOAUGyns4A1pdLzgrFVSc --single-select-option-id f75ad846
```

The same `item-edit` call, with another option id, moves the card through the transition table.

**`Status` field and option ids**: stable per project (like the hardcoded project id), so use
these directly; re-query only if a set fails:

| Field | Field id | Options: `name` → id |
| --- | --- | --- |
| `Status` | `PVTSSF_lADOAUGyns4A1pdLzgrFVSc` | Todo `f75ad846` · Blocked `cdbdc61f` · In Progress `47fc9ee4` · CI `745cb06b` · Done `98236657` |

**`gh project field-list 1 --owner UAMS-Web --format json`** re-lists every field + single-select
option id. **It costs 102 points: reach for it only when a set actually fails**, not as the
routine way to get ids the table above already pins.

### What each board call costs: the reason the rules below are rules

Projects V2 is GraphQL-only, and its 5,000 points/hour are the *same* budget every secretly-GraphQL
`gh issue` / `gh pr` / `gh release` call draws on, including `gh pr ready`, which has **no REST
fallback** at all. Measured from `wordpress-importer` against this board (1,652 items) on
2026-08-25; the row marked *(re-measured)* was re-measured from `uamswp-migration-api` against
the same board on 2026-09-05, from `X-Ratelimit-Used` header deltas:

| Call | Points |
| --- | ---: |
| `node(id:)` / `issue.projectItems` single-item verify | **1** |
| `gh project item-edit` (one field) | 1 *(re-measured: confirmed)* |
| `item-list --query '…' --limit 5` | 6 |
| `item-list --limit 30` (default) | 31 |
| `item-list --limit 400` | 405 |
| `item-list --limit 2000` | **1,718** |
| `gh project field-list` | 102 |

**`item-list` costs roughly one point per item returned**, so that 1,718 is a property of the
board's size rather than a fixed price, and one unfiltered read of this board is about a third
of the hourly budget. Filing a ticket, setting its `Status` and verifying it the way this
section describes costs a few points; verifying it by listing the board costs over a thousand.

If you re-measure this table, measure the way [`github-api-budget`](../rule-github-api-budget/SKILL.md)
prescribes: header deltas, never the `rate_limit` endpoint.

**When a list is genuinely wanted, filter server-side.** `--query` takes Projects filter syntax
and narrows before anything is returned: `--query 'is:issue is:open -status:Done'` with a small
`--limit`. That is 6 points against 1,718.

### Verify by reading the item back, never by listing the board

**Read the result back; do not report the mutation returning as the field being set.** An
exhausted GraphQL call returns `HTTP 200` with the fault in the response body (see
[`github-api-budget`](../rule-github-api-budget/SKILL.md)), so the call returning confirms nothing
on its own. Two one-point reads cover it.

**Is the issue on the board, and which one?** Ask the issue what it is on. That distinguishes
*not on a board* from *could not read the board*, and returns the project number, so an item on
the **wrong** project is not read as boarded. An empty `nodes` array is the failure:

```bash
gh api graphql -f query='query($n:Int!){ repository(owner:"UAMS-Web",name:"<repo>"){
  issue(number:$n){ projectItems(first:5){ nodes{ project{ number title } } } } } }' -F n=<issue>
```

**Is `Status` set?** Query the item by its id: exact, immune to truncation, and immune to the
issue-number collisions an org-level board carries, since numbers repeat across repos:

```bash
gh api graphql -f query='
query($id: ID!) { node(id: $id) { ... on ProjectV2Item {
  fieldValueByName(name: "Status") {
    ... on ProjectV2ItemFieldSingleSelectValue { name } } } } }' \
  -F id="$ITEM_ID"
```

> **Verify by item id (1 point); browse with `item-list --query` and a small `--limit` (6 points).**
> `item-list` costs about one point per item returned and truncates at `--limit` without an
> error, so a short read is a false negative that looks like several failed writes: on a board
> this size a `--limit` smaller than the item count returns a page that does not contain your
> item and is indistinguishable from the item being absent. Raising the limit is not the fix but
> the damage: any number written here goes stale as the board grows, and a large `--limit`
> (1,718 points at 2,000) drains the budget out from under `gh pr ready`, which has no REST
> fallback. Do not count items, and do not compare `totalCount` to `.items | length`. The
> github.com board UI can lag a few seconds before a just-set value appears, so re-read by item
> id rather than re-setting a value that looks blank in the browser. **Default triage** for an
> ordinary dev issue: on the board, `Status=Todo`, assigned to the owner.

## Archetypes at a glance

Pick the skeleton that matches the work:

- **Bug fix** → lede (with discovery provenance) · `## The bug` or `## Summary` · `## Root
  cause` (offending code) · `## Reproduction` · `## Proposed fix` (fix code) · `## Acceptance
  criteria` (ends in a regression test) · `## References`.
- **Feature** → lede · `## Why` · `## What we're building` (+ behavior detail / tables) ·
  `## Acceptance criteria` · `## Out of scope` · `## References`.
- **Research spike** → `Research:`-prefixed title · lede ("**Research spike.** … deliverable is
  a documented decision, not code") · `## Why this is a spike` · `## Questions to resolve` ·
  `## Acceptance criteria` (decisions + go/no-go) · `## References`.
- **Content / data task** → lede · `## Background` · `## Definitions` · `## Methodology` ·
  `## Acceptance criteria` · `## References`.
- **Follow-up cleanup** → `Follow-up to #N.` lede · `## Scope` · short `## Acceptance criteria`.
  `Follow-up to #N.` is provenance and stays; any dependency on `#N` is an edge.

## Tone and voice

- Technical, prose-driven, specific. Lead with *why*, then *what*. Concrete file paths, handles,
  commands, URLs, error strings over generalities.
- Bound scope deliberately: `## Out of scope` is part of writing a good issue, not an
  afterthought.
- No exclamation marks. Use `*emphasis*` sparingly, only on the word that carries the sentence.
- **Impersonal voice throughout**: every artifact posts under one account, so first person
  reads as that account narrating its own work: no `I`/`my`/`you`/`your`, and no vouching
  stance. See
  [`impersonal-voice-in-github-artifacts`](../rule-impersonal-voice-in-github-artifacts/SKILL.md).
- **No coordination plumbing**: nothing about the out-of-band channel sessions coordinate over:
  no machine aliases, no per-session labels, no liveness vocabulary. A reader of the tracker has
  no access to that channel, so a claim expressed in its terms is unverifiable to its own
  audience. Keep the evidence and drop the proper nouns: see
  [`coordination-plumbing-stays-out-of-artifacts`](../rule-coordination-plumbing-stays-out-of-artifacts/SKILL.md)
  rather than restating it here.
- **No emoji**: not in the title, the body, or any comment. A marker asserts urgency the reader
  cannot calibrate, and a glyph breaks downstream where nothing can report it. Use words: a
  bolded clause says what a glyph was standing in for. See
  [`no-emoji-in-durable-records`](../rule-no-emoji-in-durable-records/SKILL.md).

## Example shape

A compact bug issue from `uams-statamic` demonstrating the core conventions:

**Title:** `GlobalOrigin tag returns null (not '') in non-recursive mode, crashing email render`

````markdown
```
Discovered while validating the form-email rendering pipeline for #706. `App\Tags\GlobalOrigin::index()` declares a `string|array` return type, but in **non-recursive** mode it returns `null` whenever the resolved global set has no origin (the common case for a root brand). PHP then throws a `TypeError`, and because this runs inside the form-email render pipeline it crashes the entire notification email, not just the tag.

## Root cause

[`app/Tags/GlobalOrigin.php`](https://github.com/UAMS-Web/uams-statamic/blob/main/app/Tags/GlobalOrigin.php#L205-L217), non-recursive branch:

```php
$origin = $global->origin();   // null when the set has no origin (e.g. a root brand)
$result = $origin instanceof Localization ? $origin->locale() : $origin;  // null
return $result;                // returns null; signature is `: string|array`
```

The recursive branch is unaffected: it returns `[]` for an origin-less set.

## Proposed fix

Return `''` instead of `null` in the non-recursive branch so the signature holds and the documented "empty string if no origin" behavior is honored:

```php
return $origin instanceof Localization ? $origin->locale() : '';
```

## Acceptance criteria

- [ ] `{{ global_origin handle="…" }}` on an origin-less / root global set renders to `''` without throwing.
- [ ] `{{ global_origin handle="…" }}` still returns the origin site handle when an origin exists.
- [ ] Recursive mode is unchanged (`[]` for root, ancestor array otherwise).
- [ ] A regression test covers the origin-less non-recursive case.

## References

- Parent audit: #199 (every tag in `app/Tags/` is in scope)
- Discovered under: #706 (form-email rendering pipeline validation)
```
````

(Lede opens with discovery provenance and leads with the user-visible crash. `## Root cause`
quotes the offending code; `## Proposed fix` shows the one-line change. Acceptance criteria are
observable outcomes that bound both the fixed and the unaffected behavior and close with a
regression test. No AI-triage disclaimer. File path links to the absolute branch URL.)
